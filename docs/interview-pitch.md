### BopoBear｜注音符號學習 Web App

**給非母語學習者的注音學習工具**——筆順練習、拼音組合、聽力測驗、遊戲化積分

🔗 線上版：bopobear（Vercel）｜🎨 設計 + 開發：一人完成

#### 產品亮點

- **完整學習路徑**：37 符號筆順 → 雙拼音（130 組）→ 結合韻（21 組）→ 三拼音（156 音節）→ 聽力測驗
- **3D 黏土風設計系統**：從角色（台灣黑熊）到 320+ 張插圖視覺一致
- **雙語介面**（EN/JP）+ 遊戲化（積分、等級、confetti）
- **零門檻**：不註冊可完整使用，Google 登入後雲端同步進度

#### 技術架構

| 層 | 技術 |
|----|------|
| 前端 | React 19 + Vite（SPA）、React Router、Context API、hanzi-writer（筆順引擎）、Web Audio |
| 後端 | **Serverless**——Supabase（Google OAuth + PostgreSQL 進度同步）、EmailJS（回饋信）、Vercel（託管 + CDN + Analytics） |
| AI Pipeline | Gemini 圖片模型批次生成 320+ 張風格一致插圖（風格參考圖 + 自動去背）；Gemini TTS 生成 58+ 個台灣國語發音音檔——素材成本 < NT$1,000 |
| 開發流程 | **Spec-driven**：每個功能先寫 plan / requirements / validation 再實作，與 AI 協作開發 |

#### 我在專案中展現的能力

設計系統建立 ✕ 產品規劃 ✕ AI 工作流設計 ✕ 前端整合——**從 0 到上線一人閉環**

## 講稿（約 2.5 分鐘）

> **開場（20 秒）**
>
> 「BopoBear 是我獨立設計並開發的注音符號學習 Web App，目標用戶是想學注音的非母語者，
> 例如學中文的日本人。它涵蓋完整的學習路徑：從 37 個符號的筆順練習，到雙拼音、結合韻、
> 三拼音的組合學習，最後用聽力測驗驗收，全程遊戲化。」

> **設計（30 秒）**
>
> 「視覺上我建立了一套 3D 黏土風的設計系統——主角是戴紅眼鏡的台灣黑熊，
> 從介面元件到 320 多張教學插圖都維持同一種材質語言。
> 這麼大量的插圖是靠我設計的 AI pipeline 完成的：我先定義一張風格參考圖，
> 寫腳本批次呼叫 Gemini 圖片模型，再自動去背成透明 PNG。
> 320 張風格一致的插圖，成本不到一千塊台幣，而且個別不滿意可以單張重生成。」

> **技術（40 秒）**
>
> 「技術上前端是 React 加 Vite 的單頁應用，筆順動畫和描字評分用 hanzi-writer，
> 發音用 Web Audio。我刻意不自建後端，全部走 serverless：
> 身分驗證和資料庫用 Supabase——用戶不登入也能玩，進度存在瀏覽器；
> Google 登入後升級成雲端同步，這個『漸進式帳號』設計是為了降低小朋友的使用門檻。
> 意見回饋用 EmailJS 直接從前端發信，部署在 Vercel，git push 就自動上線。
> 發音音檔也是 Gemini TTS 批次生成的，過程中我處理了不少工程問題——
> 比如 TTS 對特定詞彙會拒答，我就設計了『兩詞連唸再用靜音切割』的 workaround。」

> **開發方法（30 秒）**
>
> 「開發流程我採用 spec-driven：每個功能先寫 plan、requirements、validation 三份文件，
> 確認方向後才實作，做完逐項驗收。這讓我跟 AI 協作時能維持品質——
> AI 負責產程式碼和素材，我負責規格、審核和產品決策。
> 專案裡的 specs 目錄就是一份活的產品文件。」

> **收尾（15 秒）**
>
> 「這個專案展現的是我從產品規劃、設計系統、AI 工作流設計到前端整合的一人閉環能力。
> 我可以現場展示，也歡迎看 GitHub 上的 spec 文件和 commit 歷史。」

## 預期 Q&A

**Q：為什麼不用 Next.js？**
A：這是純客戶端互動的教學工具，沒有 SEO 和伺服器渲染需求，Vite SPA 更輕量、開發迭代更快。

**Q：AI 生成的內容品質怎麼控管？**
A：三層把關——①風格參考圖鎖定視覺一致性 ②腳本自動驗證（透明度、檔案完整性）③人工逐張審核，
不合格的單張重生成（例如 AI 把「王」畫成文字、蜜蜂腳太多，都被我抓出來重做）。

**Q：資料量大了怎麼辦？**
A：目前詞彙資料都是靜態 JS 檔（約 350 筆），對這個規模是最快的方案；
若未來要 CMS 化，Supabase 的 PostgreSQL 已經在架構裡，遷移路徑很清楚。

**Q：多人協作怎麼辦？**
A：spec-driven 流程天生適合協作——specs 目錄就是 onboarding 文件，
新成員看 roadmap 和各功能的 requirements 就能接手。
